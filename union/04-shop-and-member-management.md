# 工會後台 —— 店面與會員管理（U-05）

路由前綴：`union/`　｜　認證：**會員 token**
對應 spec：§U-05、§U-05.1、§U-05.2、§U-05.3、§P-07.4

> 先讀 [共通約定](../conventions.md) 與 [工會後台總覽](README.md)。
> 租戶邊界、登入帳號與會籍的關係、回應信封都在那裡，本文件不再重複。

## 這一份文件的分界線在哪裡

§P-07.4 把處置權切成三層，而工會落在中間那一層 —— **看得到全部，動得了一部分，
且動得了的都是可逆的**：

| 工會做得到 | 工會做不到 |
| --- | --- |
| 暫停旗下店面、解除**自己所下**的暫停 | 關閉店面（不可逆） |
| 會員的**商城側**停權／恢復 | 改寫會籍主檔 `membership_status` |
| **核發旗下會員的商城帳號**（含重發憑證） | 建立會籍、改寫姓名與會員編號 |
| 建立違規記錄（`source = manual`） | 撤銷違規、裁定申訴、標記重大違規 |
| 查詢旗下店面、商品、會員與訂單摘要 | 執行退款與撥款 |

**越級的操作不是「按鈕會失敗」，多半是「路由不存在」。** 例如工會端沒有
`close`、沒有退款、沒有申訴裁定 —— 前端不要留這些入口。唯一會回 403 的越級是
「解除平台所下的停權」，因為它與工會自己所下的暫停共用同一條路由（見第 5 節）。

## 1. 旗下店面清單

```
GET union/shops
```

需要 `shop.review` @ 本工會。分頁。

| 參數 | 型別 | 說明 |
| --- | --- | --- |
| `status` | string | `approved` \| `open` \| `suspended` \| `closed` |
| `page` / `per_page` | integer | 見[共通約定](../conventions.md#分頁) |

> `shops.status` **只有這四種**。審核期的 `pending_review` / `needs_info` /
> `rejected` 在**申請單**上，不在店面上（§11.2）—— 要查審核中的案件請用
> [`GET union/shop-applications`](02-reviews.md#1-店面申請清單)。

### 回應 200

`data` 為店面陣列，形狀與平台端的店面清單相同（`ShopPresenter::detailed`）：

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `suspended_by_type` | string\|null | `seller` \| `union` \| `platform` —— **處置來源**。未暫停時為 `null` |
| `suspended_reason` | string\|null | 處置理由 |
| `approved_at` | string\|null | 申請核准（＝店面被建立）的時間 |
| `open_violation_count` | integer | **生效中**的違規筆數。已撤銷與已到期的不算 —— 那正是它們有狀態的理由 |
| `open_violation_points` | integer | 生效中的違規點數合計。§P-01 的風險指標原料 |

> **一份巡檢清單的用途就是決定要點開哪一家。** 在這兩格出現之前，
> 管理者得另外打 [`GET union/violations`](01-overview-and-queries.md#4-本工會店面的違規記錄唯讀)
> 再自己按 `shop_id` 兜起來。

> **`suspended_by_id` 不在回應裡。** 資料表有這一欄，輸出刻意不帶：
> 誰下的處置屬於稽核紀錄，工會需要知道的是**層級**（解不解得掉），
> 不是那個人的識別碼（§2.3 最小揭露）。

**來源決定誰解得開**（§11.2、§P-07.4）。前端請依 `suspended_by_type` 決定
「解除暫停」按鈕要不要出現：值為 `platform` 時工會解不掉。

## 2. 店面詳情

```
GET union/shops/{shop}
```

需要 `shop.review` @ 本工會。`data` 為店面詳情：清單單筆的全部欄位，
**外加一塊 `violations`** —— 這家店最近的違規記錄（至多 5 筆，新到舊）。

點開一家店最主要的理由就是看它有沒有事（§P-01）。清單只給**計數**、
詳情才給**明細**：一份二十列的清單各塞一份違規帳本會讓它打不開，
而那正是總覽只放數字的同一個道理。

完整的帳本（含分頁與篩選）在
[`GET union/violations?shop_id=`](01-overview-and-queries.md#4-本工會店面的違規記錄唯讀)。

> **不含銀行帳戶。** 撥款帳戶只有店主本人與平台碰得到（§S-10）——
> 工會管理者一律不得查看賣家的銀行資料，連遮罩態都不給。
> 要看戶名驗證是否通過，請看[店面申請](02-reviews.md#核准檢核清單)的
> `approval_checklist.bank_account_verified`。

跨工會的店面 ID 回 **403**，不是 404 —— 那間店確實存在，只是不歸你管（§2.3）。

## 3. 店面商品查詢

```
GET union/shops/{shop}/products
```

需要 `product.review` @ 本工會。分頁。

| 參數 | 型別 | 說明 |
| --- | --- | --- |
| `status` | string | 商品狀態，見 §11.2 的完整列舉 |
| `page` / `per_page` | integer | 見[共通約定](../conventions.md#分頁) |

**這是查詢，不是審核入口。** 工會要裁定商品請用

## 4. 暫停店面

```
PATCH union/shops/{shop}/suspend
```

需要 **`shop.dispose`** @ 本工會（不是 `shop.review` —— 審核與處置是兩回事）。

| 欄位 | 型別 | 必填 | 規則 |
| --- | --- | --- | --- |
| `reason` | string | ✅ | 最長 255 |

### 回應 200

`data.status` 為 `suspended`，`data.suspended_by_type` 為 **`union`**。

### 暫停不等於停止履約

「店面暫停或停權時既有訂單仍可完成出貨、退貨與撥款」（§P-07.2、§12.3-77）。
暫停擋的是**新交易**：商品不再可購買、不能上架新品。已成立的訂單照走完
出貨、退貨與撥款 —— 前端不要顯示成「已停業，訂單已中止」。

### 情節重大時該做什麼

工會沒有關閉店面的權限。§P-07.4 的分工是**暫停並轉平台處理** ——
先用這支端點止血，再以[建立違規記錄](#8-建立違規記錄)留下依據。

## 5. 解除暫停

```
PATCH union/shops/{shop}/resume
```

需要 `shop.dispose` @ 本工會。

| 欄位 | 型別 | 必填 | 規則 |
| --- | --- | --- | --- |
| `reason` | string | ✅ | 最長 255 |

### 誰解得開誰下的處置

| `suspended_by_type` | 工會可否解除 |
| --- | --- |
| `seller`（賣家自行暫停營業） | ✅ |
| `union`（工會所下） | ✅ |
| `platform`（平台停權） | ❌ **403**，並留下稽核紀錄 |

這是本文件唯一一個「有路由但會 403」的情形（§12.3-74）。403 的訊息會說明是
越級解除，可直接顯示給操作者 —— 下一步是聯絡平台，不是再按一次。

## 6. 會員詳情與訂單摘要

```
GET union/members/{member}
```

需要 `member.view` @ 本工會。

### 回應 200

```json
{
  "success": true,
  "message": "取得會員的店面與訂單摘要。",
  "data": {
    "member": { "…會員資料，姓名／電話／身分證皆為遮罩態…" },
    "shop": null,
    "orders_in_this_union": {
      "total": 12,
      "by_status": { "completed": 9, "refunded": 1, "cancelled": 2 },
      "note": "僅計本工會店面的子訂單；該會員在其他工會的交易不在此列 (spec §2.3)。"
    }
  },
  "errors": null,
  "meta": null
}
```

`shop` 為 `null` 是**正常狀態，不是資料缺漏** —— 多數會員只是買家（§S-01）。

### 為什麼摘要只有筆數、沒有金額

所有營業額一律走淨銷售額口徑，而那個口徑的範圍是店面／工會／平台，
**沒有買家這一維**（§11.3、§12.3-45）。在這裡自行加總應付金額會把已退款的
算成消費額 —— 那個數字看起來合理，只是虛報的。

要金額請用[匯出](#9-匯出會員商城統計)，那裡有專門的「買家實付淨額」口徑。

### 訂單摘要只計本工會

條件同時綁**買家**與**組織**。只綁買家會把該會員在其他工會的交易一併吐出來，
而那不是多給一點資訊，是跨租戶外洩（§2.3）。

## 7. 會員商城側停權與恢復

```
PATCH union/members/{member}/marketplace-status
```

需要 **`member.marketplace_dispose`** @ 本工會。

| 欄位 | 型別 | 必填 | 規則 |
| --- | --- | --- | --- |
| `status` | string | ✅ | `active` \| `suspended` |
| `reason` | string | ✅ | 最長 200 |

### 兩個狀態，兩種來源，不可混用（§2.2、§U-05.2）

| 欄位 | 來源 | 商城可否改 | 意義 |
| --- | --- | --- | --- |
| `membership_status` | 會務職行家同步 | **唯讀** | 會籍事實：`active` / `suspended` / `resigned` |
| `marketplace_status` | 工會或平台處置 | ✅ 本端點 | 商城營運處置：`active` / `suspended` |

**可交易性 = 兩者皆為 `active`。** 本端點只動後者 —— 回應會同時帶出兩個欄位，
`membership_status` 必然維持原值。工會在商城側停權一位會員，**不代表他被工會除名**，
他在其他工會的會籍與店面也完全不受影響（§12.3-76）。

### 不連動旗下店面

是否一併暫停店面由工會另行決定。自動連動看似貼心，實際上會產生一筆沒有自己理由的
處置紀錄，而 §P-07 要求每一項處置都能回溯到具體依據。

### 既有訂單照常履約

與店面暫停同一條原則：停權擋新交易，不中止既有訂單的出貨、退貨與退款。

## 8. 核發商城帳號

```
POST union/members/{member}/account
```

需要 **`member.account_issue`** @ 本工會。平台端有[同名的一支](../platform/03-organizations-and-members.md#11-核發商城帳號)，
行為完全相同，差別只在租戶範圍由 Policy 限縮。

### 為什麼工會要自己做這件事

§X-01 同步寫入的是**會籍事實**：名冊上有這個人，不代表他要用商城。因此同步建出來的
會籍 `account` 為空，登不進來。開通是「所屬組織核發」的事（§X-05.1）—— 這一支存在
之前，每一個要開通的會員都得回頭找平台，工會一多那就是人工瓶頸。

**這仍然不是改寫會籍。** `member.account_issue` 與 `member.manage` 是兩個權限：
前者開通商城帳號，後者寫會籍主檔（僅平台）。工會持有前者、沒有後者。

### 首次核發與重發是同一支

| 會員狀態 | 這一支做什麼 | `first_issue` |
| --- | --- | --- |
| `account` 為 `null` | 取號、寫入帳號、交付憑證 | `true` |
| 已有 `account` | **帳號不變**，只重新交付憑證並作廢舊連結 | `false` |

不必先問「他有帳號嗎」再決定打哪一支 —— 那個答案在會員清單的
`has_marketplace_account` 裡已經有了，而兩支的權限與稽核完全一樣。

**帳號一經核發即不可變更**（§X-05.1）：換掉它，該會員既有的訂單、評價與稽核就指向
一個他再也登不進去的識別。

| 欄位 | 型別 | 必填 | 規則 |
| --- | --- | --- | --- |
| `channel` | string | ✅ | `email` \| `sms` \| `offline` |

### 三種交付管道，以及為什麼 `offline` 要另外授權

| `channel` | 會員怎麼拿到密碼 | 經辦人看得到密碼嗎 |
| --- | --- | --- |
| `email` | 收到一次性連結，自己設定密碼 | ❌ |
| `sms` | 同上，連結走簡訊 | ❌ |
| `offline` | 經辦人把回應裡的一次性初始密碼交給他 | ✅ |

`offline` 另需 **`member.credential.offline`**，**預設不授予工會管理者**：那條管道
等於讓經辦人取得一組可直接登入該會員帳號的密碼。需要臨櫃辦理的工會請向平台申請授予。
沒有這個權限而送 `offline`，回的是 403（不是 422）—— 值域是對的，你只是沒有授權。

### 回應 200

```json
{
  "success": true,
  "message": "商城帳號已核發，初始憑證已依指定方式交付。",
  "data": {
    "member": { "…": "同會員清單單筆" },
    "account": "TPEUNION-000031",
    "credential": {
      "channel": "email",
      "destination": "w***@example.com",
      "initial_password": null,
      "expires_at": "2026-08-21T09:00:00+08:00"
    },
    "delivery": {
      "status": "delivered",
      "channel": "email",
      "destination": "w***@example.com",
      "expires_at": "2026-08-21T09:00:00+08:00",
      "failure_reason": null,
      "retryable": false
    },
    "first_issue": true
  },
  "errors": null,
  "meta": null
}
```

`offline` 時 `initial_password` 是**明文，且只會出現這一次** —— 不寫稽核，沒有第二支
查詢端點。前端必須讓經辦人當場複製或列印；掉了就再打一次這一支。

#### 交付結果是欄位，不是 HTTP 狀態

取號成功但憑證**當下送不出去**（郵件供應商、簡訊閘道故障）時仍回 **200**，
由 `delivery.status = failed` 說出交付沒成功，`retryable` 告訴你可以重打同一支。

**帳號已經核發了**——回 422 說「什麼都沒發生」是騙人的，而操作者看到錯誤就會再按
一次，第二次不取新號但他不知道。`account` 也不再只出現在訊息字串裡：
前端不必解析中文句子。

`status = failed` 時 `credential` 是空物件：**交付失敗不得降級輸出明文密碼**。
Email 送不出去就回一組初始密碼「先抄下來」，等於用一次供應商故障繞過
`member.credential.offline` 的權限分離——而那條權限預設就不給工會管理者。

完整欄位說明見[平台端同一支](../platform/03-organizations-and-members.md#delivery-欄位核發與交付是兩件事)。

### 找出還沒開通的人

```
GET union/members?account_status=pending
```

`account_status` 取 `pending`（尚未開通）或 `issued`（已開通），省略則不篩選。
同步跑完之後清單裡多半是還沒開通的人，沒有這個參數只能靠人眼翻頁。

**參數名刻意不叫 `status`**：這一頁已經有 `membership_status` 與 `marketplace_status`
兩個狀態欄位，第三個叫 `status` 的參數會讓人以為它們共用值域。

### 失敗

| 狀態 | 情況 | 訊息 |
| --- | --- | --- |
| 403 | 不是本工會的會員 | `您只能為本工會的會員核發帳號，不得跨工會存取 (spec §U-05、§2.3)。` |
| 403 | 沒有 `member.account_issue` | `您沒有核發商城帳號的授權 (spec §X-05.1)。` |
| 403 | 選 `offline` 但沒有 `member.credential.offline` | 訊息會指名改用 Email 或簡訊 |
| 422 | 會籍已退會而**尚未**有帳號 | 入會與復籍請於會務系統辦理 |
| 422 | 商城側停權而**尚未**有帳號 | 已有帳號者仍可重發 —— 停權不是刪帳號，他還有既有訂單與申訴（§P-07.2） |
| 422 | 選 `email` 卻沒有可用信箱、選 `sms` 卻沒有可用門號 | 訊息會指名改用哪種方式 |

> 422 一律**不佔號**：交付預檢跑在取號之前，因此失敗之後該會員仍是「尚未開通」，
> 補齊聯絡方式再打一次即可。退信的信箱視同沒有（§X-02）。
>
> **交付當下送不出去不在這張表裡**：那時取號已經完成，回的是 200 與
> `delivery.status = failed`。「還沒開始」與「做了一半」的下一步不同——
> 前者補資料，後者重新交付。

## 9. 建立違規記錄

```
POST union/violations
```

需要 **`violation.record`** @ 本工會。

| 欄位 | 型別 | 必填 | 規則 |
| --- | --- | --- | --- |
| `shop_id` | integer | ✅ | 必須是本工會的店面，否則 403 |
| `type` | string | ✅ | `violation_types.code`，見 `GET union/violations` 的既有值 |
| `reason` | string | ✅ | 5～500 字 —— 沒有事實描述的記錄支撐不了任何處置，更支撐不了申訴時的攻防 |
| `evidence` | string[] | — | 佐證連結，每則最長 255 |

### 回應 201

```json
{
  "data": {
    "record": { "id": 31, "source": "manual", "recorded_by_type": "member", "points": 2, "…": "…" },
    "disposition": { "level": "warned", "points": 5, "platform_points": 0, "thresholds": { "…": "…" } }
  }
}
```

### 三個被寫死的欄位

| 欄位 | 強制值 | 為什麼不開放 |
| --- | --- | --- |
| `source` | `manual` | `auto` 是排程的冪等產物，帶 `reference_type/id` 唯一鍵。讓人工入口寫得出 `auto`，等於讓人手動佔用排程的冪等鍵 |
| `recorded_by_type` | `member` | 這是雙累計的判斷依據，見下。**它會出現在回應與清單裡** —— `source` 兩邊都是 `manual`，分不出來 |
| `is_major` | **不可傳** | 重大違規不受點數門檻限制、直接停權（§P-07.1），給了工會就有一條繞過「暫停並轉平台」分工的路 |

### 雙累計：工會的點數不會讓店面被停權（§P-07.2、§12.3-84）

回應的 `disposition` 有**兩個**累計值：

| 欄位 | 涵蓋來源 | 用於 |
| --- | --- | --- |
| `points` | 全部來源（平台 ＋ 工會） | 警告、限制上架兩級門檻 |
| `platform_points` | **僅平台人員記錄者** | **停權門檻** |

工會記的點會推升 `points`，但 `platform_points` 一動也不動 —— 因此工會無法靠
累計記點把店面推進平台的不可逆處置。認為情節已達停權時，正確的動作是
[暫停店面](#4-暫停店面)並轉平台。

**兩個數字對得起來**：把 [`GET union/violations`](01-overview-and-queries.md#4-本工會店面的違規記錄唯讀)
裡 `counts_towards_points` 為 `true` 且 `recorded_by_type` **不是 `member`** 的
`points` 加總，就是 `platform_points`。對不上時是那張清單有問題，不是門檻算錯。

### 分界是「誰的判斷」，不是「人還是機器」

`recorded_by_type` 有三個值，而**只有 `member` 被排除在停權累計之外**：

| 值 | 誰 | 計入停權門檻 |
| --- | --- | :---: |
| `admin` | 平台人員人工建立 | ✅ |
| `system` | 平台的自動偵測（逾期未出貨、取消率超標，§P-07.1） | ✅ |
| `member` | 工會人工建立 | ❌ |

把 `system` 也排除掉的話，**逾期未出貨將永遠不可能導致停權** —— 而那正是
§P-07 要處置的核心行為之一。不計入的理由只對工會成立：工會無權執行、
事後也無權收回停權，因此它的記點不該間接推動那個處置。

> 這也表示 `platform_points` 可能**不是 0**，即使工會一次也沒收到平台的人工記錄
> —— 自動偵測的點數就在裡面。

### 工會不得撤銷自己建立的記錄

建立與撤銷是兩個權限（`violation.record` / `violation.manage`）。記錯了請聯絡平台 ——
違規記錄是申訴時的攻防依據，可由記錄者單方撤銷的記錄支撐不起那個角色。

## 10. 匯出會員商城統計

```
POST union/members/export
```

需要 `member.view` @ 本工會。

| 欄位 | 型別 | 必填 | 規則 |
| --- | --- | --- | --- |
| `from` | date | — | 統計區間起（含） |
| `to` | date | — | 統計區間迄（含） |

> **兩個都省略時是「本月至今」，不是全期間** —— 與總覽、賣家報表同一組區間規則
> （§11.3）。倒置的區間（`from` 晚於 `to`）回 422。
>
> **沒有 `organization_id`。** 範圍恆為操作者自己的工會；送了也不會被採用。
> 這與總覽刻意不同：總覽接受它是為了讓「跨工會存取」成為一個能被 Policy 明確
> 拒絕的請求，而匯出如果靜靜忽略它，回應會看起來完全正常，只是算的不是你
> 以為的那個工會。

### 回應 201

`data` 為匯出紀錄，含 `id`、`row_count`、`period` 與建立時間。
**檔案不在這個回應裡** —— 下載是另一支端點（第 11 節），因為「下載須先有一筆
已授權的匯出紀錄」是這條規則的實作方式（§2.3）。

### 檔案內容

每一位會員一列：

| 欄位 | 說明 |
| --- | --- |
| `member_number` | 會員編號 |
| `name` / `phone` | **遮罩態** |
| `membership_status` / `marketplace_status` | 兩個狀態並列，來源不同 |
| `paid_order_count` | 已付款訂單筆數 |
| `gross_payable` | Σ 應付金額 |
| `refunded_amount` | Σ 已處理退款 |
| `net_paid` | **買家實付淨額** = `gross_payable` − `refunded_amount` |

檔頭另有 `summary`（總額 = 明細加總，§12.3-58）、`basis`（口徑字串）、
`period`、`masking_note` 與 `scope_note`。

### 「買家實付淨額」不是「淨銷售額」

兩者算式不同，**刻意取了不同的名字**：

    淨銷售額（賣家／工會／平台）= Σ 應付 − Σ 已處理退款 − Σ 負向調整
    買家實付淨額（本檔）        = Σ 應付 − Σ 已處理退款

差在負向調整 —— 那是拒付或對帳差異時**對賣家的追扣**（§14.6），與買家付了多少錢
無關。算式不同的數字掛同一個名字，遲早有人把它們加在一起。

### 不含身分證與繳費狀態

身分證連遮罩態都不給：遮罩值在檔案裡沒有任何用途，而一份帶著幾百個遮罩身分證的
檔案仍然是個資檔（§2.3、§X-05.4）。繳費狀態是會務端的事實，商城不該成為它的
第二個發布管道（§B-01）。

### 查無資料時給空報表

沒有交易的工會也匯得出一份**空結果報表**（`row_count: 0`），不是錯誤檔（§S-09）。

## 12. 下載匯出檔

```
GET union/members/exports/{export}/download
```

需要 `member.view` @ 本工會。回應是**檔案串流**，不是 JSON 信封。

**別的工會的匯出紀錄 ID 回 404，不是 403。** 租戶條件寫在查詢裡，因此那筆紀錄
對你而言根本不存在 —— 回 403 等於告訴對方「這個編號是有效的，只是不給你」，
而那本身就是一則跨租戶資訊（§2.3）。

找不到實體檔案時**同樣回 404**（檔案過期或已清理）。兩種情形回應相同是刻意的：
呼叫端不需要、也不應該分辨得出來。

> 這與[店面詳情](#2-店面詳情)的 403 不同，兩者的差別值得記一下：店面是**跨租戶
> 可見的資源**（商品在前台看得到），因此拒絕用 403；匯出檔是**本工會產製的私有
> 檔案**，別人根本不該知道它存在。

**每一次下載都留稽核**，並累加該筆紀錄的 `download_count` 與
`last_downloaded_at`（見第 10 節的回應）—— 下載是**資料真正離開系統的那一刻**，
產製當下反而不是（§S-09、§P-03）。

## 13. 會務同步異常時的行為（§U-05.3）

[`GET union/overview`](01-overview-and-queries.md#1-工會商城總覽) 一律帶
`member_sync` 區塊：

| 欄位 | 意義 |
| --- | --- |
| `has_ever_synced` | 同步**接了沒有**。判準是有沒有跑過任何一輪批次 |
| `is_failing` | 最近一次嘗試不是合格成功 —— **現在**壞著 |
| `is_stale` | 距最後一次**合格完整成功**已逾 `member_sync_stale_hours` |
| `last_complete_success_at` | 最後一次合格完整成功的**來源觀測時間** |
| `last_synced_at` | 同上（保留舊欄位名） |
| `last_attempt` | 最近一次嘗試的狀態、時間、錯誤、`qualified` 與 `safety_assessment` |
| `stale_after_hours` | 現行門檻 |

`last_attempt.safety_assessment` 是同步實際寫入前的差異摘要；尚未執行新版預檢的歷史
批次為 `null`。其中 `blocked=true` 代表來源縮減或預計退會比例達系統參數門檻，整輪
在任何會員異動前中止。摘要同時保存當輪使用的兩個百分比門檻及最低影響筆數，
避免日後調整參數後無法還原當時為何被擋；它只含人數與比例，不含姓名、身分證或會員編號。

### 為什麼要分這麼多欄位

**「最近一次嘗試」與「最近一次成功」必須分開。** 合成一個「最後同步時間」，
一個連續失敗三天的組織會顯示成三天前同步過——那是真的，而看的人會以為只是
有點舊，不是壞了。

**判準是批次，不是 `members.synced_at`。** 逐筆時間只說明「至少有一個人在那個
時間被同步過」。一輪跑到一半炸掉的批次，前一千筆已經寫了 `synced_at`，於是整個
組織看起來剛剛才同步完，而後面幾千筆的會籍是舊的——**失敗越接近開頭，看起來
越健康**。

**新鮮度看 `source_observed_at`，不看 `finished_at`。** 一輪批次可能跑好幾個
小時；以完成時間計算等於讓一份開始時就已經陳舊的名冊在結束時重新變新。

**`qualified` 與 `status` 不同。** `status = succeeded` 只代表跑完了。合格還要求
來源確實讀到資料（空名冊多半是統編接錯），且沒有無法對接的會籍（那些人的會籍
狀態這一輪根本沒被更新）。「跑完了」與「跑對了」是兩件事，只有後者能解除防護。

### 三種「沒有成功時間」不能混為一談

| 情形 | 判準 | 處置 |
| --- | --- | --- |
| 尚未接同步（人工維護的工會、平台預設組織） | 一輪都沒跑過 | **正常**，不擋 |
| 已接同步但**從未成功** | 跑過、無合格成功 | 擋——這份資料從來沒有可信過 |
| 曾經成功但已逾期 | 有合格成功、但太舊 | 擋 |

舊版把後兩者一併當成「從未同步過」而放行，於是首次同步失敗變成一個**看不見**
的狀態：工會接上了同步、第一輪就壞了，而系統的行為與完全沒接同步時一模一樣。

### `is_stale = true` 時被暫停的是「以會籍為條件的處置」

「同步異常時暫停以會籍為條件的處置，不得以逾期資料判定」。具體來說：

| 動作 | 同步逾期時 |
| --- | --- |
| 核准開店申請（檢核含「有效會員」「已繳費」） | **422**，訊息說明資料不可信 |
| 唯讀查詢（本文件 1、2、3、6、10、11 節） | 照常 —— 查詢正是判斷故障範圍的方式 |
| 商城側停權、店面暫停、建立違規記錄 | 照常 —— 這些不讀會籍事實 |

回 **422 而不是 403**：那不是權限問題，是資料不可信，而兩者的下一步完全不同。
